# 🍳 爱心小厨房 Love Kitchen

一个**两人共用**的点菜微信小程序：翻菜单、加点想吃的、备注辣度忌口，掌勺人在待做看板上照着做菜。适合情侣 / 家人搭伙做饭，也适合作为「微信小程序 + 云数据库」的入门学习项目。

> 📘 **完整技术文档** → [`docs/项目全解.md`](docs/项目全解.md)
> 面向会翻代码的人：技术选型的三次反复、数据层四层与 id 双号段、权限模型、样式分层、契约测试护栏、62 次提交的迭代史，以及每一条设计取舍背后的理由与代价。
>
> 本文（README）讲**怎么用、怎么跑起来**；项目全解讲**为什么这么做**。

## ✨ 功能特性

- 🔍 **搜索找菜**：支持菜名、食材、分类模糊搜索；多关键词用空格分隔（如「鸡 汤」）；可与分类筛选叠加
- 📖 **菜单分类浏览**：经典热菜 / 凉菜腌腊 / 汤羹煲 / 小吃点心 / 米粉主食（已预置 303 道菜（江西特色 + 家常大全），**内置在代码里，零配置即可用**）
- 🌶️ **每道菜单独选辣度**：点「＋」时选（默认就是推荐辣度），同一道菜可以点两种辣度分开算（你微辣、他特辣）
- 🛒 **购物车下单**：数量加减、逐道改辣度、一键下单、下单署名
- 💬 **订单备注**：辣度、忌口、想说的小留言
- 🚫 **忌口随订单一起送到厨房**：干饭人在「我的资料」记的忌口清单（最多 12 条），**下单时会跟着订单一起送到掌勺人那边** —— 待做看板和订单卡片上顶出一条红边警示「🚫 TA 不吃：香菜、花生」。点菜时就在结算页看得见、临时还能补一条；改单重新提交也会同步。**没记忌口就不占位置**，不摆一条空的在那里
- 🍚🧑‍🍳 **两种身份各管一摊**：**干饭人**只管点单（点单 / 我的订单 / 我的资料），**掌勺人**管待做 + 菜单（待做 / 菜单 / 订单 / 我的资料）—— 掌勺人点不了单、干饭人推不了状态，放同一台手机也不会误触
- 🪞 **两边的资料各存各的**：「我的资料」里的头像 / 称呼 / 个人介绍 / 当前状态 / 忌口清单**按身份分开存**（`lovekitchen_*_cook` 与 `lovekitchen_*_orderer` 两套 key）—— 编辑其中一方的基本信息不会改动另一方；换身份只是换一份资料来看，互不干扰
- 🧑‍🍳 **订单状态跟踪**：待开做 → 开做中 → 已上菜，掌勺人在待做页或订单页都能推进
- 🙅 **驳回也要说理由**：掌勺人做不了这一单（食材不够 / 来不及 / 太难）就点「驳回」，**必须写一句为什么**（还给了几个一键快捷说法）。理由会直接摆到干饭人的订单卡片上；干饭人改一改重新提交，这一单自动回到「待开做」。掌勺人**只能更新状态或驳回，改不了干饭人点的单**（菜品 / 备注 / 用餐时间一个字都动不了，删单也不行）
- ✏️ **订单随时可改**：干饭人改菜、改辣度、加减数量、改备注、改署名，或整单删掉（**开做中**不能改也不能删 —— 掌勺人已经开火了，做完以后随删；已上菜的终态只可删）；**状态不归他管** —— 编辑页里状态只有一行只读展示
- 🎲 **今天吃什么**：选择困难症一键随机推荐
- ➕ **自助维护菜单**：两种身份都能加菜、改菜、下架
- 📋 **菜单日志（掌勺人）**：干饭人对菜单做过的**加菜 / 改菜 / 下架**记成一页流水，按天分组、改动明细一行一处（「辣度 微辣 → 中辣」），TA 动的带粉色竖条一眼可辨。菜单存在各自手机里，不记这一笔就永远不知道 TA 动过什么
- 📥 **CSV 批量加菜**：整理好的菜单一次导进来 —— 支持**从微信聊天选文件 / 读剪贴板 / 直接粘贴**，逗号 CSV 与 Excel 复制的制表符都能认；**先解析预览再写**（区分新增 / 覆盖 / 跳过 / 有问题），还能一键复制模板、导出当前菜单去电脑上改完再导回来
- 🍳 **今日待做看板**：按一日三餐分格，没点的格子也留着，一眼看出哪顿还没安排
- ⏰ **点单截止 + 到点提醒**：每顿饭有自己的点单截止时刻（**早餐 10:00 / 午餐 14:30 / 晚餐 19:30 / 夜宵 23:30**，见 `utils/constants.js`），过了就只能订下一顿；**截止前半小时如果这单还没开做，掌勺人手上会弹一次提醒**（「宝贝的午餐 14:30 截止，还没开做」），点「这就去做」直接落到待做看板。一单只提醒一次，不唠叨
- 🔥 **菜单按点菜频率排（掌勺人）**：掌勺人的菜单默认把**干饭人点得最多的菜排在前面**，点过 2 次以上的标「🔥 TA 点过 N 次」—— 三百多道菜里一眼看出该盯着哪几道备料；右上角胶囊可切回默认顺序（干饭人的「点单」页始终是原顺序，免得熟悉的位置天天变）
- ⭐ **逐道菜评价**：干饭人对「已上菜」的单，可以给**每一道菜单独打分**（1~5 星 + 快捷标签 + 一句话），掌勺人在订单页就能看到反馈；同一道菜改一改再存就是更新，评错了可撤销
- ⚡ **实时同步点单情况**：干饭人点完单，掌勺人这边会自己冒出来（待做页浮提示 + 底栏角标）；掌勺人一动火，干饭人那边状态自己变。不需要下拉刷新，也不用退出重进
- 🔔 **底栏数字角标**：掌勺人「待做」显示**有几单等着开做**，干饭人「我的订单」显示**有几单正在做 + 有几单被驳回**

## 🛠 技术栈

| 层    | 技术                                              |
| ---- | ----------------------------------------------- |
| 前端   | 微信原生小程序（WXML / WXSS / JS），零框架、业务代码零第三方依赖       |
| 菜单数据 | **内置在代码里**（`data/dishes.js`，303 道菜），**零后台配置即可用**   |
| 订单存储 | WorkBuddy 云服务 · **PostgreSQL**（关系型数据库）                |
| 订单访问 | **小程序直连**（`@tencent-ai/workbuddy-cloud-sdk/miniprogram`，`wx.request` 走固定网关） |
| 权限控制 | 数据库侧行级 `RLS 策略`（云服务已预配好，业务代码零权限代码） |

> **为什么菜单要内置、订单才进数据库？**
> 菜单是静态数据（303 道菜，一年也改不了几次），内置进代码最快：零后台配置、离线可用、读取零延迟。
> 订单必须两个人共享，所以要进真数据库。至于为什么是「小程序直连」而不是「云函数中转」，见下方说明。

### 为什么订单不用云函数？为什么不用自建云开发？

订单后端踩过两条路，都放弃了，最终落在 WorkBuddy 云服务上：

1. **云函数（`wx.cloud.callFunction`）**：云函数运行环境**不注入微信用户身份（JWT）**，访问数据库只能以「匿名」身份进行，PG 上默认只有读权限，写入直接报 `permission denied`；想让云函数写库还得配管理员 API Key —— 对个人项目既麻烦又容易配错。
2. **自建云开发 + 小程序直连 PG**：官方为小程序直连设计的路径，但有一个隐藏门槛 —— **云开发环境必须绑定当前小程序的 AppID**。本项目当时用的环境是平台代建腾讯云账号创建的，`WxAppId` 为空，在开发者工具里绑不上，`wx.cloud` 压根不会出现，「直连」无从谈起。
3. **WorkBuddy 云服务（现状）**：自带固定网关和授权体系，小程序端**零密钥** —— 只需要一个公开的 `publishableKey`（仅标识应用、不带权限）+ SDK 自动装配的 `wx.request` 通道。权限由数据库侧 RLS 把关，业务代码里没有任何权限逻辑。

这条路径也正好符合「两个人共享同一份订单」的需求。

## 🚀 快速开始

### 1. 克隆并导入

```bash
git clone https://github.com/wanshunzhong-ai/love-kitchen.git
```

打开「微信开发者工具」→ 导入项目 → 选择仓库目录。AppID 填你自己的小程序 AppID（仓库中的 AppID 可直接替换）。

### 2. 直接编译，就能看到 303 道菜 ✅

**这一步不需要任何后台配置。** 菜单数据已内置在 `data/dishes.js`，点「编译」即可浏览菜单、加购物车。按「预览」扫码，手机也能看。

订单功能依赖的 SDK（`@tencent-ai/workbuddy-cloud-sdk`）**已按官方规范构建好放在仓库的 `miniprogram_npm/` 目录**，克隆下来即可用，**不需要执行 npm install / 构建 npm**。

> 该 SDK 的小程序入口是打包出的自包含单文件（零外部 `require`），因此可以离线复现构建产物。
> 需要重新生成时（升级 SDK 版本后）执行 `node scripts/build-npm.js`，或用开发者工具的「工具 → 构建 npm」。
> 若小程序报「暂不支持 npm 模块」，先重新编译 → 清缓存重开项目 → 最后才考虑重新构建。

### 3. 编译运行（订单功能开箱即用）

点「编译」，即可浏览菜单、加购物车、下单。按「预览」扫码，手机也能看。

- **不需要建表**：云服务环境里的 `orders` 表和权限策略已就绪，业务代码零 DDL。
- **不需要配域名**：SDK 走小程序专用固定网关，发布流程会自动把网关域名登记进微信的 request 合法域名，开发期在工具里也不受域名校验影响。
- **真机调试**报 `800059 file not found` 时：工具内「清除缓存 → 重新编译」，或关闭项目重新打开（文件索引缓存问题）。

### 4. 发布体验版（想让对方用手机访问时）

1. 开发者工具右上角「**上传**」→ 填版本号（如 `1.0.1`）。
2. mp.weixin.qq.com → 管理 → 版本管理 → 开发版本 →「**选为体验版**」。
3. 成员管理 → 体验成员 → 把对方的微信号加进去。
4. 体验版二维码发给对方即可。

> 对方打开时**不需要再做任何配置**：数据库连接和权限都在小程序内部完成，对方只要被加进体验成员即可。

## ☁️ 数据模型

**dishes（菜单）** — 内置数据，见 `data/dishes.js`

| 字段          | 类型     | 说明                   |
| ----------- | ------ | -------------------- |
| id          | number | 主键（**纯数字**，本地服务分配）   |
| name        | string | 菜名                   |
| category    | string | 分类，默认 '经典热菜'         |
| emoji       | string | 展示图标，默认 '🍴'         |
| spice       | string | 辣度：不辣 / 微辣 / 中辣 / 特辣 |
| description | string | 介绍                   |
| created_at  | number | 创建时间（毫秒时间戳）          |

> **id 必须是纯数字**：`pages/checkout` 用 `Number(dataset.id)` 做购物车加减，字符串 id 会得到 `NaN` 导致加减失效。
> 用户在小程序里加菜 / 改菜会写入**本地覆盖层**（`wx.setStorageSync('dishes_override_v1')`），不改动内置数据；删除内置菜则记入黑名单 `dishes_deleted_v1`，避免重启后「复活」。

**orders（订单）** — WorkBuddy 云服务 PostgreSQL 表（随云服务环境预建）

| 字段              | 类型          | 说明                                         |
| --------------- | ----------- | ------------------------------------------ |
| id              | BIGINT      | 主键（自增，**经接口返回为字符串**以免精度丢失）                 |
| items           | JSONB       | 菜品快照 `[{dishId, name, emoji, spice, qty}]` |
| remark          | TEXT        | 订单备注，默认空串                                  |
| order_by        | TEXT        | 谁点的（昵称），默认 '宝贝'                           |
| owner_openid    | TEXT        | 下单人 openid，默认空串（预留字段，当前未使用）                |
| status          | TEXT        | pending（待开做）/ cooking（开做中）/ done（已上菜）/ rejected（已驳回） |
| reject_reason   | TEXT        | 最近一次驳回的理由，默认空串（只在 status = rejected 时展示；重新提交时清空） |
| rejected_at     | TIMESTAMPTZ | 驳回时刻，可为空                                 |
| reviews         | JSONB       | 逐道菜的评价 `{ "dishId\|辣度": {rating, tags, text, by, at} }`，默认 `{}` |
| avoids          | JSONB       | 下单时干饭人的忌口快照 `["香菜","花生"]`，默认 `[]`（随订单冻结，掌勺人据此避雷） |
| created_at      | TIMESTAMPTZ | 创建时间，默认 `now()`                            |
| updated_at      | TIMESTAMPTZ | 更新时间，默认 `now()`                            |

约束与索引：

- `CHECK (status IN ('pending','cooking','done','rejected'))` —— 状态只允许这四个值，脏数据进不来
- `orders_created_at_idx ON orders (created_at DESC)` —— 订单按时间倒序列表走索引
- `orders_status_idx ON orders (status)` —— 按状态筛选（订单页有「已驳回」筛选）

> **items 里的 `spice` 是用户下单时选定的辣度**，不一定等于菜品自身的推荐辣度。
> 同一道菜如果点了两种辣度，会在 `items` 里存成两条独立记录（`dishId` 相同、`spice` 不同），各自带自己的数量。
> 购物车同理：条目以「菜 + 辣度」为唯一键（`dishId|spice`），因此改数量、删除都只影响对应那一条。
>
> **`reviews` 用「对象 + 键」而不是数组**：键是菜品行标识（`dishId|辣度`，与购物车 / 编辑页同一套规则）。
> 对象按键查找天然保证「同一道菜只有一条评价」不会被写重复，读取也是 O(1)。
> 写入是**单条 upsert**：服务端读出当前的 `reviews`、按 key 合并、再整体写回 ——
> 两个人同时评价不同的菜时不会互相覆盖。星级传 0（或不传 review）等于撤销那一条。
> 服务端还会校验「这道菜确实在这一单里」和「订单已经上菜」，不指望前端自觉。
>
> **`created_at` / `updated_at` 返回给页面时会被转成毫秒数**：PG 的 `timestamptz` 取回来是 ISO 字符串，而页面层 `utils/format.js` 的 `formatTime` 期望毫秒数，转换逻辑在 `utils/orders.js` 的 `toMillis()`。

**dish_logs（菜单操作日志）** — WorkBuddy 云服务 PostgreSQL 表

| 字段           | 类型          | 说明                                                           |
| ------------ | ----------- | ------------------------------------------------------------ |
| id           | BIGSERIAL   | 主键（自增）                                                       |
| action       | TEXT        | add（加菜）/ update（改菜）/ delete（下架）/ import（批量导入），有 CHECK 约束     |
| dish_id      | BIGINT      | 目标菜品 id；批量导入没有单一目标，为 NULL                                     |
| dish_name    | TEXT        | **操作当时的菜名快照** —— 菜品后来被删也读得懂，所以它是流水账，不是从菜品表 join 出来的视图        |
| changes      | JSONB       | 改了哪些字段 `[{"field":"辣度","from":"微辣","to":"中辣"}]`，只有 update 非空 |
| dish_count   | INTEGER     | 批量导入的道数，单条操作固定 1                                             |
| by_role      | TEXT        | orderer（干饭人）/ cook（掌勺人），有 CHECK 约束                           |
| by_name      | TEXT        | 操作当时的昵称快照（对方后来改了称呼，历史日志仍显示当时那个名字）                             |
| created_at   | TIMESTAMPTZ | 操作时刻，默认 `now()`                                              |

约束与索引：

- `CHECK (action IN ('add','update','delete','import'))`
- `CHECK (by_role IN ('orderer','cook'))`
- `dish_logs_created_at_idx ON dish_logs (created_at DESC)` —— 日志页按时间倒序取最近 200 条

> **这张表只给 `SELECT` + `INSERT`**（orders 是四个都给）：日志是审计流水，不该被改写 —— 没有推进状态、没有删单这类需求。若日后加「清空历史日志」，再单独开权限并配套页面入口。
> 真机部署时新表记得**两个角色都授**（`authenticated` 与 `anon`，实际落到 `anon`，原因见迁移 `20260928160000_orders_anon_grant.sql`）。

### 🔐 权限模型（关键，出问题先看这里）

PostgreSQL 的权限是**两层**的，两层都通过才成功：

| 层    | 内容                          | 说明                 |
| ---- | --------------------------- | ------------------ |
| 第一层  | 表级 `GRANT`                  | 决定这个角色「能不能碰这张表」    |
| 第二层  | 行级 `RLS 策略`                 | 决定这个角色「能碰表里的哪些行」   |

`orders` 表已启用 RLS，策略配为「**打开这个小程序的人可读、可写全部订单**」——因为订单是「两个人共享同一份」的语义，不需要按人隔离。

这些都在云服务环境里**预先配好**，业务代码里没有任何权限逻辑。两点值得知道：

> **RLS 的本质是「默认拒绝一切」**：只要表启用了 RLS 却没有匹配的策略，所有操作都会被拒绝。
> 所以「表建好了但读不出来 / 写不进去」几乎一定是策略没配或没配全，而不是代码问题。
>
> **前端手里的 `publishableKey` 不是密钥**：它只标识「是哪个应用」，本身不带任何权限；
> 真正的权限边界在数据库 RLS。前端代码里永远不会出现有权限的密钥。

## 🔌 接口

所有前端调用都通过 `utils/api.js` 的 `call(action, payload)` 发出。菜品走本地实现，订单走 PostgreSQL：

| action              | 走向 | 参数                                   | 说明                       |
| ------------------- | -- | ------------------------------------ | ------------------------ |
| `listDishes`        | 本地 | `{ category?, keyword? }`            | 拉取菜品（支持分类 / 关键词过滤）       |
| `getDish`           | 本地 | `{ id }`                             | 取单道菜                     |
| `saveDish`          | 本地 | `{ id?, payload }`                   | 新增（无 id）或增量修改（有 id）      |
| `deleteDish`        | 本地 | `{ id }`                             | 下架菜品（幂等）                 |
| `importDishes`      | 本地 | `{ items }`                          | **批量加菜**：整批只落一次盘；带 `id` 走更新，不带则按同名找（找不到才新增） |
| `listOrders`        | PG | —                                    | 拉取最近 200 条订单，按创建时间倒序     |
| `createOrder`       | PG | `{ payload: { items, remark, order_by, avoids } }` | 下单（`avoids` = 干饭人的忌口快照，随订单送给掌勺人） |
| `getOrder`          | PG | `{ id }`                             | 取单笔订单（编辑页用），不存在返回 `null` |
| `updateOrder`       | PG | `{ id, payload }`                    | **改内容**（只有干饭人该调）：菜品 / 备注 / 署名 / 用餐时间 / 忌口。**不接受 status**；已上菜拒改；被驳回的单改完自动退回「待开做」并清掉理由 |
| `updateOrderStatus` | PG | `{ id, status }`                     | **推进状态**（只有掌勺人该调）：`pending` / `cooking` / `done`；传 `rejected` 会被拒（驳回必须带理由） |
| `rejectOrder`       | PG | `{ id, reason }`                     | **驳回**（只有掌勺人该调）：理由必填（≤60 字），待开做 / 开做中才能驳 |
| `deleteOrder`       | PG | `{ id }`                             | 删除订单（干饭人删自己点的单）          |
| `saveReview`        | PG | `{ id, key, review }`                | 保存一道菜的评价；`review` 传 `null` 或星级 0 = 撤销 |

> **订单的权限边界写在三处，改之前三处一起看**：
> ① 页面层：`pages/orders` 按 `isCook` 出不同的按钮（掌勺人只有「开始做 / 做好了 / 驳回 / 收回驳回」，干饭人只有「编辑 / 评价 / 删掉」）；
> `pages/order-edit` 对掌勺人退化成只读详情；`pages/todo` 的卡片上也只给状态与驳回。
> ② 数据层：`utils/orders.js` 的 `updateOrder` 不认 `status`、`updateOrderStatus` 不认 `rejected`、`rejectOrder` 理由必填。
> ③ 规则层：`utils/reject.js` 一个 `canReject(status)`，页面与服务端引同一份，不会各写一套后漂移。

> 想给订单加新接口？在 `utils/orders.js` 里加一个函数，挂进 `ACTIONS` 表，再把 action 名加进 `utils/api.js` 的 `ORDER_ACTIONS` 数组即可。

## 📥 CSV 批量加菜

菜单入口右上角的「📥 批量」进 `pages/dish-import`。能力边界与设计取舍：

**内容怎么进来**（小程序没有通用文件选择器，所以给了三条路）

| 方式 | 适用场景 | 用到的能力 |
| ---- | ---- | ---- |
| 从微信聊天选文件 | 已经把 `.csv` 发给自己了 | `wx.chooseMessageFile` + `wx.getFileSystemManager().readFile('utf-8')` |
| 读剪贴板 | 在电脑上从 Excel / WPS 复制，回手机一点粘上 | `wx.getClipboardData` |
| 手动粘贴 | 临时改几行，或前两条走不通时的兜底 | `textarea` |

**分隔符自动识别**：首个有效行里制表符多于逗号就按 TSV 解析，否则按 CSV —— 因为 **Excel / WPS 复制出来是制表符分隔的**，不认这个的话「复制粘贴」这条路直接废掉。（嗅探会跳过空行与 `#` 注释行，否则注释里那个逗号能把一份 TSV 判成 CSV。）

**注释行**：首格以 `#` 开头的整行跳过，且**在表头识别之前**就丢掉（一行注释当头会被判成「没有表头」，整份文件按固定列序读 → 全文错位）。有了它，「复制模板」给出的填写说明才敢和表格放进同一段文本里 —— 否则用户把整段粘回输入框时，那 9 行说明会被**悄悄当成 9 道菜导进去**（每行第一格「菜名：必填」恰好没超长，解析器不会报错，这种失败最难发现）。

**行号是原文的真实行号**（`utils/csv.js::lineNumbersOf`）：注释行占的位置算进去、字段引号内的换行也算进去。用数组下标当行号看着一样，但只要文件里有注释或换行字段，「第 3 行」就会被报成「第 12 行」，用户拿着行号去文件里根本找不到。

**列的顺序**：首行认得出「菜名」这一列就当表头（支持中英文别名、列序任意、大小写与空格归一化）；认不出就按 `菜名, 分类, 图标, 辣度, 介绍` 固定列序。CSV 本体是手写状态机，支持引号包裹（字段里可以放逗号、换行、`""` 转义）、CRLF / LF / CR 三种换行、UTF-8 BOM。

**字段规整的取向是「尽量收进来」，不是「报错弹回去」**（`utils/csv.js::sanitizeDish`）：

- 分类不在 `CATEGORIES` 里 → 归到「其他」；辣度不认识 → 按 `🌶️` 数量猜；图标位置写了文字 → 换成该分类的默认图标
- 每次自动纠正都会在预览里留一条 ⚠️，让用户知道改了什么
- **只有「没有菜名」才算真错误**（没名字的菜点不了单），进「没读懂的行」列表并带上行号与原始内容
- 菜名 / 介绍超长自动截断，上限与 `pages/dish-edit` 的输入框一致（20 / 60 字）

**写入语义**（`utils/dishes.js::importDishes`）

- **整批只落一次盘**。不做成「页面循环调 `saveDish`」是因为后者每次都 `loadOverride() + saveOverride()`，导 200 道菜就是 400 次同步存储读写，真机上会明显卡住
- 带 `id` → 更新那道菜；不带 `id` → **先按菜名找，找到就更新它**，否则同一道菜会被导成两份，购物车里会出现两条一模一样的
- 默认「同名跳过」，也可以在预览页切成「同名覆盖」；文件内部重名只留第一条
- 曾进过删除黑名单的菜，被导回来即视为**重新上架**
- 服务端会再规整一遍字段，前端漏校也写不进脏数据

**编码坑**：只认 UTF-8。中文 Windows 的 Excel 默认存 GBK，按 UTF-8 读出来是满屏 `�` —— 页面检测到替换字符就直接提示「另存为 UTF-8」，而不是让你对着一堆乱码猜。

**导出与模板**：「复制模板」给三道示例 + 以 `#` 开头的填写说明；「导出菜单」把当前全部菜导出去改。两者都走**剪贴板**，所以用**制表符**分隔（`utils/csv.js::buildTSV`）—— Excel / WPS 只认制表符分列，逗号文本会整段挤进一个格子，还得手动「数据 → 分列」。解析器两种都认，所以粘回来照样能导。落文件的模板仍然用 CSV（选文件器只认 `.csv` / `.txt`）。

### 配套的 CSV 文件（`templates/`）

仓库里直接放了一份，不用进小程序也能先拿到：

| 文件 | 用途 |
| --- | --- |
| `templates/爱心小厨房-加菜模板.csv` | 空白模板：表头 + 3 道示例 + 5 行留白 |
| `templates/爱心小厨房-当前菜单.csv` | 当前菜单全部 303 道，适合整体改名 / 改分类，改完直接导回来 |
| `templates/填写说明.md` | 列的含义、导入步骤、七个容易踩的点 |

这两个 CSV 都带 **UTF-8 BOM + CRLF** —— 中文 Windows 的 Excel 双击打开不带 BOM 的 UTF-8 会按 GBK 解码成乱码，加了 BOM 才是「双击即正确」。解析器本来就剥 BOM，所以对导回没有副作用。

菜单有改动后重跑 `node scripts/gen-csv-template.js` 重新生成；`.workbuddy/tmp/test_csv_template.js` 会把这些文件**再喂回解析器逐字段比对**，钉住「导出 → 改 → 导回」的无损性（含逗号 / 引号 / 换行的转义往返）。

> 这份文件放在 `templates/`，已加进 `project.config.json` 的 `packOptions.ignore` —— `.csv` 不在微信上传包的白名单后缀里，不忽略会被打上传。

## ⚡ 实时同步是怎么做的

云服务 SDK 只提供 `database / auth / storage / llm` 四个模块，**没有 realtime 订阅、也没有长连接** —— 小程序端拿不到推送通道，所以「实时」只能靠前台轮询来逼近。既然只能轮询，重点就落在「轮得聪明」上。

轮询器只有**一个**，起在 `app.js` 的 `onShow`，退到后台立刻 `onHide` 停掉（后台的定时器会被系统限流，留着只会耗电）。页面不各开各的，只做两件事：**订阅数据把列表重画一遍**、**发现变化时浮一句话提示**。

**三档节奏，跟着注意力走**（`utils/live.js` 的 `INTERVALS`）：

| 情况                          | 间隔   |
| --------------------------- | ---- |
| 掌勺人有待开做的单 / 干饭人有菜在做或有单被驳回  | 15s  |
| 有事但不急（比如还有单没上菜，但没在做的）      | 30s  |
| 全都上完菜了                      | 60s  |

> 「已驳回」是单独一档：它不计入掌勺人的「等着开做」，也不用他做任何事；
> 但干饭人要看一眼（改单或删掉），所以进干饭人的角标、也走 15 秒那一档。

连续失败时按 15s → 30s → 60s → **120s** 翻倍退避，成功后立刻回到正常档 —— 断网时不能死循环猛敲接口。手动操作（下拉刷新、重试、「开始做/做好了」）则直接强制补一轮，不受档位限制。

**变化检测 = 快照 + 差异**：每轮把订单列表压成 `{ id: {status, dishes, qty, reviews, dine} }` 再和上一份比，算出「新来几单 / 哪单改状态了 / 哪道菜被评价了」。首轮**只建基线、不报任何变化** —— 否则一进页面就会把历史订单全算成「刚来的新单」，炸出一堆提示。

**只在该说话时说话**：变化会浮一条 6 秒自动消失的提示条（不是 `showToast`，因为提示条要能被点击跳转），同时底栏角标跟着跳。掌勺人自己点的「开始做」不会再提示一遍，干饭人自己下的单也不提示 —— 自己刚做的动作重复播报一遍纯属噪音。

**一次请求办两件事**：轮到的订单列表直接喂给页面渲染，「刷新列表」和「发现变化」共用同一次请求，不额外多发。二次确认弹窗期间会临时暂停轮询（列表不能在对话框底下自己变），离开页面时把暂停状态还回去，不会把全局轮询锁死。

## 🔥 菜单按点菜频率排（掌勺人）

掌勺人的「菜单」默认**把干饭人点得最多的菜排在最前面**，点过 2 次以上的菜标一行「🔥 TA 点过 N 次」（`utils/frequency.js`）。三百多道菜，凭记忆找不出「哪几道最常做」，按频率排一眼就知道该盯着哪几道备料。右上角的胶囊可以随时切回菜单原来的顺序。

**只给掌勺人排**：干饭人的「点单」页始终保持菜单原顺序 —— 他们熟悉的位置天天变反而难找菜。所以排序写在 `isCook && sortByFreq` 上，判断在页面层，`utils/frequency.js` 本身与身份无关（纯函数，可单测）。

**三条数频率的规则**（都在 `utils/frequency.js` 里写明了理由）：

| 规则 | 为什么 |
| --- | --- |
| **被驳回的订单不算** | 那顿没做成，算进去「点得多」就变味了 |
| **一行算一次**，份数另记 | 「点过 5 次」说的是 5 单里有这道菜；一份 3 个的那行只算 1 次（份数记在 `orderQty`，用于次数相同时的排序） |
| **id 与菜名两套键都查** | 老订单的 `items` 里只有菜名没有 `dishId`；同命中时相加 |

统计范围与 `listOrders` 的取单上限一致（**最近 200 单**）。

**不额外发请求**：App 级轮询本来就在拿订单列表，菜单页直接 `live.subscribe` 订阅同一份数据 —— 干饭人一点单，掌勺人菜单的顺序自己就变了。只有轮询还没跑起来（`live.hasData()` 为假）时才自己拉一次 `listOrders`；读失败就静默按原顺序显示，不打扰人。

**统计没变就不重排**：轮询每 15 秒来一轮，每轮都整表重排会让掌勺人正在看的列表自己往上跳。所以先算一个「频率签名」（`signature()`，与键的插入顺序无关）跟上一轮比，一样就直接 return，连 `setData` 都不发。

## 🚫 忌口随订单送到掌勺人

干饭人在「我的资料」维护的忌口清单（最多 12 条），**下单时会跟着订单一起送到掌勺人那边**：待做看板和订单卡片上顶出一条红边警示「🚫 TA 不吃：香菜、花生、肥肉」，结算页和编辑订单页也各露一次脸（能看、能临时补一条）。

### 为什么必须写进订单

掌勺人的手机**读不到干饭人的本地存储** —— 忌口只有跟着订单一起上云，对方才看得见。这跟菜品 `items` 是同一个道理，所以 `avoids` 也用**快照语义**：下单那一刻的清单冻结在订单里。干饭人后来添了新忌口，不会倒回去改历史订单（「这一顿当时是按那份忌口做的」这件事不该被改）。

### 规则只有一份

忌口是自由文本，从输入到落库要过三道手（资料页录入 → 本地存储 → 随订单上云），每处各写一套收敛规则迟早会「页面里存进去了、服务端当脏数据丢掉」。所以收敛只定义一次：

**`utils/avoids.js`** —— trim → 去重 → 单条限长 10 字 → 最多 12 条。`utils/store.js`（本地存）与 `utils/orders.js`（写库前 + 读出来时）都引它，页面层不自己动手。

读出来那一侧也收敛一遍：库里万一进了旧版本写的脏数据，页面拿到的仍是干净数组。

### 两侧读的不是同一个来源

| 谁 | 看到的是 | 为什么 |
| --- | --- | --- |
| 掌勺人 | **订单里的快照**（`order.avoids`） | 他本地没有对方的清单，只能看订单上来的那份 |
| 干饭人 | **自己当前的清单**（`store.getAvoids()`） | 下单 / 改单时提交的就是它，所见即所提交 |

同一张编辑页两种身份读两个来源，别合并成一处 —— 合并了要么掌勺人看不到忌口，要么干饭人改不了清单。

### 空的时候不摆空壳

没记忌口 → `avoids` 是空数组 → `avoidsText` 是空串 → 卡片上那一整条**不渲染**，不占位置也不留一句「暂无」。掌勺人那边看到的只有真有忌口的单子。

### 下单与改单都会同步

- `createOrder` 写入快照（提交那一刻现取 storage，不用页面里的副本）。
- `updateOrder` **传了才改**（`undefined` 表示这次不动它）：编辑页改完菜会带上最新清单一起更新；万一有别的调用方不带这个字段，也不会把已有忌口抹成空 —— 那等于告诉掌勺人「TA 什么都吃」。
- 开做中的单本来就改不了，所以不会出现「照着旧忌口做菜」。

## 📋 菜单日志（掌勺人）

掌勺人的菜单页多了一行「📋 菜单日志」，点进去是干饭人对菜单做过的**加菜 / 改菜 / 下架**流水：按天分组（今天 / 昨天 / 9月28日），改菜会逐行列出变化（「辣度 微辣 → 中辣」）。TA 动的那些带粉色竖条 + 蜜桃底，从一堆记录里一眼挑得出来；顶部可切「只看 TA 动的」。

### 为什么非得单独记一笔

菜单是**本地优先**的：303 道菜内置在代码里，用户加 / 改 / 删写在各自动手机的 storage（`dishes_override_v1` / `dishes_deleted_v1`）。好处是零后台可用、离线能看；代价是**干饭人动了菜单，掌勺人的手机完全无感** —— 菜单不会跟着变，也不会收到任何提示。

```
干饭人手机：改了菜单 ──✕── 掌勺人手机看不到（各存各的）
                  └──→ 云端 dish_logs 表 ──→ 掌勺人的「菜单日志」看得到
```

所以**菜单本身照旧各存各的**（这次没动它），但「谁动过菜单」这件事必须走云端 —— 跟订单、忌口同一个道理：跨设备的信息，只有上了云对方才读得到。

### 几个刻意的决定

**写日志绝不影响加菜。** `utils/dish-logs.js` 的 `record()` 内部全静默：云端挂了、没构建 npm，加菜照样成功，只是没记上（控制台留一句，且只提示一次）。菜品库是本地功能，不能因为附属的日志把它拖垮。埋点处一律不 `await`。

**埋点埋在服务层，不在页面层。** 三处埋点都在 `utils/dishes.js` —— 它是所有改动的必经之路（加菜页 / 批量导入页 / 将来任何新入口都走这几个 action），埋在这儿才能保证「菜单变了就一定有日志」。

**只列真的变了的字段。** 点开保存但什么都没改，不记 —— 否则日志里会堆一串「什么都没发生」，要紧的改动被淹掉。

**批量导入只记一条汇总。** 一次导 200 道菜若逐条写，日志瞬间报废；掌勺人真正想知道的是「TA 一次往菜单里塞了两百道菜」。

**下架的菜名在删之前取。** 删完再查，override 里已经没了、seed 那条可能刚被拉黑，日志就只剩一个光秃秃的 id。

**规则只有一份。** 动作枚举、字段中文名、文案生成全在 `utils/dish-logs.js`；`utils/dishes.js` 只埋点、页面只渲染。字段名存的是**中文名快照**（「辣度」而不是 `spice`），将来字段改名了历史日志仍读得懂。

### 云连接也顺手收了一份

`utils/orders.js` 原本自带一整套 SDK 加载 / 客户端实例 / 诊断包装。订单与日志连的是同一个云，两处各写一套迟早出现「订单连得上、日志连不上」这种极难排查的问题，所以抽成了 **`utils/cloud.js`**（`getCloud` / `getDB` / `unwrap` / `PUBLIC_CONFIG`），两边共用同一个客户端实例。

顺带把 **SDK 改成懒加载**：`require('utils/cloud.js')` 现在零副作用，纯本地的模块（如 `utils/dishes.js`）可以放心引用日志模块，单测和静态检查里也不必装 SDK 桩。

## ⏰ 点单截止与「该做饭了」提醒

每顿饭有自己的**点单截止时刻**，过了就只能订下一顿：

| 时段 | 截止时刻 |
| --- | --- |
| 🌅 早餐 | 10:00 |
| ☀️ 午餐 | 14:30 |
| 🌙 晚餐 | 19:30 |
| ✨ 夜宵 | 23:30 |

时刻定义在 `utils/constants.js` 的 `DINE_SLOTS`（`endHour` + `endMinute` 两个字段，
是分钟精度而不是写死的整点）。结算页与改单页的时段胶囊上直接显示这两个时间，
过了的自动变灰点不动 —— 「几点前得点」一眼可见，不用点一下才知道已经订不了。

**到点提醒**：截止前 30 分钟，如果这一单**还没开做**（状态仍是「待开做」），
掌勺人那边会弹一次窗 —— 标题「⏰ 还有 25 分钟」，正文写清楚是谁的哪一顿、
几点截止、几道菜；点「这就去做」直接落到待做看板，点「知道了」就安静收起来。
同一时刻有多单到点会合成一个弹窗列出来，不会连环弹。

三条刻意的取舍（理由都写在 `utils/deadline.js` 里）：

- **只提醒掌勺人**。「还没开始做」这件事只有他能动，提醒下单的人只会让 TA 干着急。
- **状态不是「待开做」的一律不管**。正在做 / 已上菜不必催；被驳回的单球已经回到
  干饭人那边（等 TA 改了重新提交），这时候催掌勺人是催错人。
- **窗口是 `[截止 - 30 分钟, 截止)`**。过了截止就不再提醒 —— 那时候该看的是
  「哪单超时没做」，再弹一次「快到了」也来不及了。

**每单只提醒一次**：提醒过的记在本地（`lovekitchen_reminded`，最多留 60 条），
去重键是 `订单 id | 用餐日期 | 时段` —— 干饭人把用餐时间改掉就是一件新的事，
值得再提醒一次。

**提醒只可能在对方正开着小程序时出现**：云服务 SDK 没有推送通道（见上一节），
小程序关着收不到任何东西。所以它是挂在 App 级轮询上的 —— 掌勺人翻菜单、
看订单时都能被提醒到，不必停在待做页干等。

> 顺带补上的一个空档：夜宵截止从原来的 24:00 提到 23:30 之后，
> **23:30～24:00 之间今天四个时段会全部关闭**。这时「今天」会自动标灰、
> 默认日期落到明天 —— 否则会订出一单「今天的早餐」，永远做不出来。

## ❓ 常见问题

**Q：手机真机 / 体验版提示「菜单没加载出来」？**
菜单是内置数据，正常不会出现。若出现，检查是不是改坏了 `data/dishes.js`（在开发者工具「调试器 → Console」看报错）。

**Q：下单报「下单没成功：…」？**
失败提示里带了真实原因，先读提示本身。通用排查：① 确认网络可用；② 真机上打开调试（右上角「…」→ 开发调试）后在 vConsole 里找 `[WorkBuddy Cloud] request failed` 日志 —— 里面带了方法、地址、HTTP 状态码和错误信息，是最直接的线索；③ 若显示 `url not in domain list`，说明网关域名还没登记进微信合法域名（正式发布流程会自动登记，工具调试期可临时勾选「不校验合法域名」验证）。

**Q：小程序报「暂不支持 npm 模块：@tencent-ai/workbuddy-cloud-sdk」？**
按顺序排查：① 确认 `miniprogram_npm/@tencent-ai/workbuddy-cloud-sdk/index.js` 存在；② 重新点「编译」；③ 「工具 → 清除缓存 → 清除全部缓存」后**关闭项目重新打开**再编译；④ 仍不行就项目根目录 `npm install` 后执行「工具 → 构建 npm」（或 `node scripts/build-npm.js`）。

**Q：改完代码后订单功能突然不好用了？**
先想想是不是刚改过 `package.json`。改动依赖后要 `npm install` 并重新构建（`node scripts/build-npm.js` 或「工具 → 构建 npm」）。

**Q：真机调试报 800059 file not found？**
开发者工具的文件索引缓存问题：清除缓存 → 重新编译；无效则关闭项目重新打开。

**Q：云服务的免费额度会过期吗？**
WorkBuddy 云服务有免费额度（数据库读写量、存储量等），日常两人点菜的用量远够不到上限。额度详情在 WorkBuddy 的「设置 → 数据管理」面板可查。好消息：**菜单在代码里，永远不会丢**，风险只涉及订单数据。

**Q：菜品超过 100 道还能拉全吗？**
可以。内置数据不受此限制。订单侧 `listOrders` 一次最多取 200 条（`range(0, 199)`），日常使用绰绰有余；超出后只显示最近 200 条。
