## 一、项目是什么

### 1.1 一句话

一个**给女朋友点菜的小程序**：她翻菜单、加点想吃的、备注辣度忌口；我打开待做看板，照着做菜，做好了推一下状态，她那边自己就变了。

两个人、两台手机、一份共享的订单 —— 这是整个项目所有设计取舍的出发点。

### 1.2 缘起

问题很具体：**"今天吃什么"这件事，沟通成本比做饭本身还高。**

```
她："晚上吃什么？"
我："你想吃啥？"
她："都行。"
（循环）
```

这个循环里真正的信息只有两条：**她想吃什么**、**我知不知道她想吃什么**。但表达与确认的过程要来回好几轮，而且常常发生在两个人不在一起的时候（我在公司、她在学校）。

所以这个项目的目标从一开始就很明确：

> **把「两个人商量吃什么」这件事，压缩成「她点一下、我看一眼」。**

这条目标决定了后来的很多设计：

- **她只需要点，不需要学** —— 点单页要能一眼看懂，搜索要能按食材找（不记得菜名也能点）
- **我只需要照着做** —— 待做看板按早/午/晚分格，一眼看出哪顿还没安排
- **沟通要发生在产品里，不要发生在聊天框里** —— 辣度、忌口、备注、驳回理由，全部结构化落到订单上，不靠口头传达

### 1.3 两个使用者

系统只有两个角色，一开机就二选一（`pages/role-select` 是冷启动首页）：

| 身份 | 代号 | 干什么 | 默认首页 | 底栏 tab |
| --- | --- | --- | --- | --- |
| 干饭人 | `orderer` | 点单、改单、删单、评价 | 点单 | 点单 / 我的订单 / 我的资料（3 个） |
| 掌勺人 | `cook` | 看板、做菜、推状态、驳回、维护菜单 | 待做 | 待做 / 菜单 / 订单 / 我的资料（4 个） |

**"掌勺人点不了单、干饭人推不了状态"** —— 这条边界不是安全考虑（两个人共用一台手机也不稀奇），而是**防手滑**：身份决定了按钮出不出，而不是点了以后才报错。

> 身份不只是换个首页，它同时决定：底栏出几个 tab、页面出哪些按钮、`utils/live.js` 的优先级档位、菜单要不要按点菜频率排、角标数什么。判断集中在 `store.getRole()` 一处，分支留在页面层。

## 二、功能全景

### 2.1 干饭人（她能看到什么）

**点单页**（`pages/menu`，一页两用）

- 5 个分类横滑筛选 + 关键词搜索（**支持菜名、食材、分类模糊匹配**，多关键词用空格分隔，如 `鸡 汤`）
- 每道菜单独选辣度：点「＋」时弹出辣度选择，默认是这道菜的推荐辣度
- **同一道菜可以点两种辣度分开算**（她微辣、我特辣 → 购物车里是两条独立记录）
- 长列表分页：首屏只渲染 30 道，滚到底再放一页
- 「今天吃什么」随机推荐（选择困难症出口）

**结算页**（`pages/checkout`）

- 数量加减、逐道改辣度、单菜备注
- 用餐日期 + 时段胶囊（早 / 午 / 晚 / 夜宵），**过了截止时刻的时段自动变灰点不动**
- 忌口清单在这里露一次脸（能看、能临时补一条）
- 署名

**我的订单**（`pages/orders`）

- 全部订单列表，带状态筛选
- 能改内容：改菜、改辣度、加减数量、改备注、改署名、整单删掉
- **开做中不能改也不能删** —— 掌勺人已经开火了；已上菜的终态只可删
- 对「已上菜」的单，逐道菜打分评价
- 被驳回的单会显示理由，「改一改重新提交」会自动回到待开做

**评价**（`pages/review`）

- 对**每一道菜**单独打分（1~5 星 + 快捷标签 + 一句话）
- 同一道菜改一改再存就是更新，评错了可撤销（传 0 星 = 撤销）

**我的资料**（`pages/profile`）

- 头像、称呼、个人介绍、当前状态
- 忌口清单（最多 12 条）
- **按身份分开存**：`lovekitchen_*_cook` 与 `lovekitchen_*_orderer` 两套 key，编辑一方不会改动另一方

### 2.2 掌勺人（我能看到什么）

**待做看板**（`pages/todo`，掌勺人首页）

- 按**今天的一日三餐**分格，**没点的格子也留着** —— 一眼看出哪顿还没安排
- 卡片上直接操作：开始做 / 做好了 / 驳回
- 订单带忌口时，卡片顶出一条红边警示「🚫 TA 不吃：香菜、花生」

**菜单管理**（`pages/menu`，同一页的另一个形态）

- 加菜 / 改菜 / 下架（两种身份都有这个入口）
- **按点菜频率排**：默认把干饭人点得最多的菜排前面，点过 2 次以上标「🔥 TA 点过 N 次」；右上角胶囊可切回原顺序
- 📥 批量加菜入口
- 📋 菜单日志入口

**订单**（`pages/orders`）

- 全部订单；掌勺人的按钮只有「开始做 / 做好了 / 驳回 / 收回驳回」
- **改不了干饭人点的单**：菜品、备注、用餐时间一个字都动不了，也不能删单

**菜单日志**（`pages/dish-logs`，非 tab 页）

- 干饭人对菜单做过的**加菜 / 改菜 / 下架**流水，按天分组
- 改菜逐行列出变化：「辣度 微辣 → 中辣」
- TA 动的记录带粉色竖条一眼可辨，顶部可切「只看 TA 动的」
- 默认 30 天窗口 + 200 条上限，「看更早的 ›」按 ×3 扩窗

### 2.3 两个人共享的能力

| 能力 | 说明 |
| --- | --- |
| **实时同步** | 她点完单我这边自己冒出来（浮提示 + 底栏角标）；我一动火她那边状态自己变。不用下拉刷新 |
| **底栏角标** | 掌勺人「待做」= 有几单等着开做；干饭人「我的订单」= 有几单正在做 + 几单被驳回 |
| **驳回要写理由** | 做不了就驳回，**必须写一句为什么**（给了 actionSheet 快捷说法 + 末项自己写）。理由直接摆到她的订单卡片上 |
| **忌口随单走** | 她的忌口清单下单时跟着订单上云，我这边看板与订单卡片顶红边警示 |
| **到点提醒** | 截止前 30 分钟若这单还没开做，我手机上弹一次「⏰ 还有 25 分钟」，点「这就去做」直接落到看板 |
| **批量加菜** | CSV / TSV 导入，三条入口（微信聊天选文件 / 读剪贴板 / 手动粘贴），先解析预览再写 |
| **断网感知** | 断网时全局 toast「网络断开了，恢复后订单会自动同步」，恢复时补一句 |

## 三、技术选型与理由

### 3.1 技术栈

| 层 | 技术 | 选它的理由 |
| --- | --- | --- |
| 前端 | 微信原生小程序（WXML / WXSS / JS） | 两个人用的小工具，上框架的收益抵不过构建链的复杂度；原生小程序零依赖、体积小、真机行为可预测 |
| 菜单数据 | **内置在代码里**（`data/dishes.js`，303 道） | 静态数据，一年也改不了几次 —— 内置即零配置、离线可用、读取零延迟 |
| 订单存储 | WorkBuddy 云服务 · **PostgreSQL** | 订单必须两个人共享，必须有真数据库 |
| 订单访问 | **小程序直连**（`@tencent-ai/workbuddy-cloud-sdk/miniprogram`） | 固定网关 + 零密钥，业务代码里没有任何鉴权逻辑 |
| 权限控制 | 数据库侧 `GRANT` + 行级 `RLS 策略` | 权限边界下沉到数据库，前端拿不到有权限的凭据 |
| 状态管理 | 无框架，`utils/store.js` 本地存储 + App 级轮询 | 页面各自 `setData`，跨页共享的只有订单和身份 |

**业务代码零第三方依赖**（`package.json` 里唯一的依赖是云服务 SDK，且已构建产物随仓库提供）。

### 3.2 后端为什么换了三次

这条路踩过两个坑，最终才落在现在这套上 —— 过程比结论有价值。

**第一次：云函数（`wx.cloud.callFunction`）—— 失败**

云函数运行环境**不注入微信用户身份（JWT）**。这意味着云函数访问数据库只能以「匿名」身份进行，而 PG 上匿名默认只有读权限，写入直接 `permission denied`。

想让云函数能写库，得去配管理员 API Key —— 对一个个人项目来说既麻烦又容易配错，而且把「一个有全库权限的凭据」放进云函数环境变量，安全性上也不划算。

**第二次：自建云开发 + 小程序直连 PG —— 失败**

这是官方为「小程序直连数据库」设计的路径，看起来最正统。但有一个隐藏门槛：**云开发环境必须绑定当前小程序的 AppID**。

本项目当时用的环境是平台代建腾讯云账号创建的，`WxAppId` 为空。结果是在开发者工具里**绑不上**，`wx.cloud` 压根不会出现 —— 「直连」无从谈起。这个问题排查起来很费劲，因为报错信息指向的是「未开通云开发」，而实际上云开发是开着的，只是绑不了这个 AppID。

**第三次：WorkBuddy 云服务 —— 成功（现状）**

自带固定网关和授权体系，小程序端**零密钥**：

- 前端只需要一个公开的 `publishableKey` —— **它只标识「是哪个应用」，本身不带任何权限**
- SDK 自动装配 `wx.request` 通道，发布流程会把网关域名登记进微信的 request 合法域名
- 权限由数据库侧 RLS 把关，**业务代码里没有任何权限逻辑**

### 3.3 为什么菜单内置、订单上云

这不是「偷懒」，是两种数据的性质不同：

| | 菜单 | 订单 |
| --- | --- | --- |
| 谁改 | 我们俩偶尔加一两道 | 她点单、我推状态，随时在动 |
| 要不要共享 | 内置 303 道两台手机**本来就有同一份** | 必须共享 —— 她点的单我要看得到 |
| 改的频率 | 一年改不了几次 | 每天多次 |
| 结论 | **内置进代码** | **进真数据库** |

菜单内置带来的直接好处：**克隆下来直接编译就能用，零后台配置**。这也是这个项目能被人直接跑起来的原因。

代价是「她改了菜单我看不到」—— 这个问题后来用 `dish_logs` 日志表和一个单向共享链补上了（见 [6.2](#62-菜品库本地优先--一条单向共享链)）。

### 3.4 为什么「实时」是轮询而不是推送

**因为 SDK 没有推送通道。**

云服务 SDK 只提供 `database / auth / storage / llm` 四个模块 —— **没有 realtime 订阅、没有长连接、没有服务端推送**。小程序端拿不到任何推送通道。

既然只能轮询，重点就从「能不能实时」变成「**轮得聪不聪明**」：

- 轮询器**全局只有一个**，起在 `app.js` 的 `onShow`，退到后台立刻 `onHide` 停掉
- **三档节奏跟着注意力走**：有事要做 15s、有事但不急 30s、都做完了 60s
- **增量拉取**：每轮只拉「id + status + updated_at」三列轻量头，只为「新的 / 变了的」拉详情
- **失败退避**：连续失败 15s → 30s → 60s → 120s 翻倍，成功后立刻回到正常档

详见 [第九章](#九实时同步与到点提醒)。

### 5.2 页面层的三条约定

**① 每个 tab 页 `onShow` 都要做三件事**（漏一件就会出现「切回来没反应」或「身份串了」）：

```js
onShow() {
  this.getTabBar().setData({ selected: N })   // 底栏选中态（自定义 tabBar 不会自动同步）
  this.refresh()                              // 拉数据重画
  store.ensureRole()                          // 身份守卫（没选身份 → 踢回 role-select）
}
```

**② 非 tab 页不设 `ensureRole` 门槛。** `checkout` / `order-edit` / `review` 等页面**两种身份都能进**，页面内只按 `store.getRole()` 决定形态。这条被 `test_roles.js` 钉着 —— 曾经有人在 `order-edit` 加了身份门槛，结果掌勺人点订单卡片直接进不去。

**③ 跳转方式不能混。**

| 目标 | 用哪个 | 为什么 |
| --- | --- | --- |
| tab 页（menu / orders / todo / profile） | `wx.switchTab` | `navigateTo` 会**静默失败**，且 tab 页不能进页面栈 |
| 非 tab 页 | `wx.navigateTo` | 正常入栈 |

### 5.4 分页

`utils/paging.js`（零依赖零副作用）：`PAGE_SIZE = 30` / `initial` / `hasMore` / `grow` / `slice` / `clamp`。

落点 **2 处**：`pages/menu` + `components/dish-picker`。（组件化之后，order-edit 与 dish-editor 都不再直接渲染菜品列表，全走 dish-picker。）

**前缀不变式**：渲染的列表永远是完整列表的 `slice(0, shown)` —— 于是 wxml 里 `data-idx="{{index}}"` 与完整列表下标**天然一致**，分页**不会**让原有「按 index 取元素」的代码错位。

这条不变式是有代价的：`slice` 每次都要复制数组。但换来的是「加一个取元素的地方不用去想分页」，值。

### 6.2 菜品库：本地优先 + 一条单向共享链

#### 分层

| 层 | 位置 | 说明 |
| --- | --- | --- |
| **seed** | `data/dishes.js` | 内置 **303 道**，id `1..303`，由 `scripts/merge-template-dishes.js` 生成，**勿手工编辑** |
| **override** | 本地 storage `dishes_override_v1` | 应用内新增 / 编辑的菜，按 id 覆盖 seed |
| **deletedIds** | 本地 storage `dishes_deleted_v1` | 删掉的 seed 菜 id 黑名单（否则刷新后 seed 会让它「复活」） |
| **shared** | 云表 `public.dishes` | **只放掌勺人新增的菜**（共享增量层） |

#### 为什么只同步一条单向链

内置 303 道**两台手机本来就有同一份**（都在代码里），不需要同步。所以「菜单对不齐」只发生在**应用内加的菜**上 —— 而且两条链**根本不对称**：

| 方向 | 现状 |
| --- | --- |
| 干饭人加菜 → 掌勺人 | **本来就通** —— 下单时 `orders.items` 是快照，菜名跟单过去；另有 `dish_logs` 记了一笔 |
| 掌勺人加菜 → 干饭人 | **原先完全不通** —— 干饭人点单页读的是自己手机的菜单，看不到、点不到 |

后来只补了后一条，而且**刻意不做双向**：

> **只加不减、没有改名、没有下架 → 不需要冲突处理。**

成本约为完整双向同步的 1/4。反过来，「干饭人加的菜只留本机」是刻意的 —— 她加的菜八成是「今天想吃这个」，下单时菜名进了 `orders.items` 快照，我照样看得到，没必要让她的菜单也同步过来。

#### id 双号段（「不撞号」的唯一保证）

这是这块最容易踩的地方。

- **分界**：`constants.CLOUD_ID_BASE = 100001`
- `< 100001` **本地号段**：内置 seed + 本机加的菜，**两台手机各自发号**
- `≥ 100001` **云端号段**：云表 identity 发号，两台手机同一个 id

**为什么必须分号段**：本地自增在两台手机上**从同一个数起步**（都从 seed 长度往后排）。如果本地 id 能直接当云端 id 用，两台手机各自加的第 304 道菜会**都是 304** —— 撞号，云端一 merge 就互相覆盖。

因此：

> **`nextId()` 与 `importDishes` 的 cursor 都必须显式跳过云端号段。**

#### 写路径：先本地落盘 + 事后 rekey

```
掌勺人新增一道菜
  │
  ├─ 1. 本地落盘（本地号段 id + pendingSync 标记）
  │      → 立刻成功、离线可用、**不 await**
  │
  ├─ 2. 推上云 pushAdd → 拿到云端 id
  │
  ├─ 3. rekey：把本地那一行换成云端 id，并清掉 pendingSync
  │
  └─ 4. 推失败 → 静默留着标记，下次 sync() 补推
```

**「先本地落盘、不 await」是关键**：菜单是本地功能，加一道菜不该因为网络慢而卡住界面。云端同步是「事后补上」的动作。

#### 合并规则（唯一实现 `utils/dish-cloud.js::mergeInto`，纯函数）

按序三条，顺序不能换：

1. **本地拉黑过 → 跳过**（不复活）
2. **本地 `localEdited` → 不覆盖**（本地优先）
3. **否则**：没有就插入、有就按云端更新

三条补充事实：

- 内置菜的 id **永不在云端表里** → 这条链**碰不到内置菜**
- **「内容一样」不算更新**（否则每次 `onShow` 都白重画一遍列表）
- `dish-cloud.js` 的网络函数**失败一律静默**（返回 `null` / `false`，从不抛错）—— 菜单是本地功能，云端挂了必须还能读、还能改内置菜

#### 接线点

菜单页 `onShow` 调 `syncShared()`，**必须放在 `loadDishes()` 之后** —— 别让网络请求挡住首屏渲染。只有 `added` / `updated` 非零才重画。

#### 云表 `public.dishes` 的结构约定

- identity 列**从 100001 起**（C30 改造时 `RESTART WITH 100001`）
- 有 `by_name`（谁加的，快照）与 `updated_at`
- RLS 策略 `dishes_couple_all` + `anon` / `authenticated` 的 ALL GRANT 都在
- 内置 303 道**不进表**
- 导入上限 `csv.IMPORT_MAX = 500`（曾是 300，菜单超过 300 之后「导回去」会被截断）

### 6.3 订单

**表结构 `public.orders`**

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `id` | BIGINT | 主键自增（**经接口返回为字符串**，避免 JS 精度丢失） |
| `items` | JSONB | 菜品快照 `[{dishId, name, emoji, spice, qty}]` |
| `remark` | TEXT | 订单备注，默认空串 |
| `order_by` | TEXT | 谁点的（昵称），默认 `'宝贝'` |
| `owner_openid` | TEXT | 预留字段，当前未使用 |
| `status` | TEXT | `pending` / `cooking` / `done` / `rejected` |
| `reject_reason` | TEXT | 最近一次驳回理由（只在 `rejected` 时展示；重新提交时清空） |
| `rejected_at` | TIMESTAMPTZ | 驳回时刻 |
| `reviews` | JSONB | 逐道菜评价 `{ "dishId\|辣度": {rating, tags, text, by, at} }`，默认 `{}` |
| `avoids` | JSONB | 下单时干饭人的忌口快照，默认 `[]` |
| `created_at` / `updated_at` | TIMESTAMPTZ | 默认 `now()` |

**约束与索引**

- `CHECK (status IN ('pending','cooking','done','rejected'))` —— 脏状态进不来
- `orders_created_at_idx ON orders (created_at DESC)` —— 列表按时间倒序走索引
- `orders_status_idx ON orders (status)` —— 状态筛选走索引

**三个关键设计**

**① `items` 里的 `spice` 是「下单时选定的辣度」**，不一定等于菜品自身的推荐辣度。同一道菜点两种辣度 → `items` 里两条独立记录（`dishId` 相同、`spice` 不同），各自带自己的数量。

购物车同理：条目以 **「菜 + 辣度」为唯一键（`dishId|spice`）**，所以改数量、删除都只影响对应那一条。

**② `reviews` 用「对象 + 键」而不是数组。**

键是菜品行标识 `dishId|辣度`，与购物车、编辑页**同一套规则**。对象按键查找天然保证「同一道菜只有一条评价」，读取也是 O(1)。

写入是**单条 upsert**：服务端读出当前 `reviews` → 按 key 合并 → 整体写回。两个人同时评价**不同的菜**时不会互相覆盖。星级传 0（或不传 review）等于撤销那一条。

服务端还会校验「这道菜确实在这一单里」和「订单已经上菜」，**不指望前端自觉**。

**③ 时间字段返回给页面时会被转成毫秒数。**

PG 的 `timestamptz` 取回来是 ISO 字符串，而页面层 `utils/format.js::formatTime` 期望毫秒数。转换逻辑集中在 `utils/orders.js::toMillis()`。

#### 快照语义（贯穿全项目的一条原则）

> **`orders.items` 与 `orders.avoids` 都是「下单那一刻冻结的快照」，事后改不倒推。**

这条原则的根源是一个物理事实：

> **掌勺人的手机读不到干饭人的本地存储。**

所以任何「干饭人的本地数据要给掌勺人看」的需求，**都必须写进订单上云**。忌口清单是这样，她加的自定义菜也是这样。

于是：她后来添了新忌口，**不会倒回去改历史订单** —— 「这一顿当时是按那份忌口做的」这件事不该被改。

忌口收敛（trim → 去重 → 单条 10 字 → 最多 12 条）唯一实现在 `utils/avoids.js`，`store.js`（本地存）与 `orders.js`（写库前 + 读出来时）都引它。

**`pages/order-edit` 一张页面两种身份读两个来源**（最容易踩的一处）：

| 谁 | 读到的是 | 为什么 |
| --- | --- | --- |
| 掌勺人 | `order.avoids`（订单快照） | 他本地没有对方的清单 |
| 干饭人 | `store.getAvoids()`（自己当前清单） | 所见即所提交 |

**合并成一处必坏一头** —— 要么掌勺人看不到忌口，要么干饭人改不了清单。

#### `updated_at` 是「这条动过没」的唯一信号

`utils/orders.js` 的每条写路径都写它：

| 操作 | 是否写 `updated_at` |
| --- | --- |
| `updateOrder`（改内容） | 显式写 |
| `updateOrderStatus`（推进状态） | 显式写 |
| `rejectOrder` / `withdrawReject`（驳回 / 收回） | 显式写 |
| `saveReview`（评价） | 显式写 |
| `createOrder`（新增） | 走列的 `DEFAULT now()` |
| 删除 | 不写 —— 靠「头列表里消失」发现 |

这条表是增量轮询的地基（见 [6.6](#66-订单的增量轮询c8)）。

### 6.4 菜单日志 `dish_logs`

**append-only 审计表，只给 `SELECT` + `INSERT`**（无 UPDATE / DELETE 权限）。

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `id` | BIGSERIAL | 主键 |
| `action` | TEXT | `add` / `update` / `delete` / `import`，有 CHECK |
| `dish_id` | BIGINT | 目标菜品 id；批量导入为 NULL |
| `dish_name` | TEXT | **操作当时的菜名快照** |
| `changes` | JSONB | `[{"field":"辣度","from":"微辣","to":"中辣"}]`，只有 update 非空 |
| `dish_count` | INTEGER | 批量导入的道数，单条操作固定 1 |
| `by_role` | TEXT | `orderer` / `cook`，有 CHECK |
| `by_name` | TEXT | 操作当时的昵称快照 |
| `created_at` | TIMESTAMPTZ | 默认 `now()` |

**为什么非得单独记一笔**

菜单是本地优先的 —— 她动了菜单，**我的手机完全无感**：

```
干饭人手机：改了菜单 ──✕── 掌勺人手机看不到（各存各的）
                  └──→ 云端 dish_logs 表 ──→ 掌勺人的「菜单日志」看得到
```

所以**菜单本身照旧各存各的，但「谁动过菜单」这件事必须走云端** —— 跟订单、忌口同一个道理。

**六个刻意的决定**

| 决定 | 理由 |
| --- | --- |
| **写日志绝不影响加菜** | `record()` 内部全静默：云端挂了、没构建 npm，加菜照样成功，只是没记上。埋点处一律不 `await` |
| **埋点在服务层，不在页面层** | 三处埋点都在 `utils/dishes.js` —— 它是所有改动的必经之路，埋这儿才能保证「菜单变了就一定有日志」 |
| **只列真的变了的字段** | 点开保存但什么都没改不记 —— 否则日志堆一串「什么都没发生」，要紧的改动被淹掉 |
| **批量导入只记一条汇总** | 一次导 200 道若逐条写，日志瞬间报废；我真正想知道的是「她一次塞了两百道菜」 |
| **下架的菜名在删之前取** | 删完再查，override 里已经没了、seed 那条可能刚被拉黑，日志只剩一个光秃秃的 id |
| **规则只有一份** | 动作枚举、字段中文名、文案生成全在 `utils/dish-logs.js`；`dishes.js` 只埋点、页面只渲染 |

**字段名存中文快照**（「辣度」而不是键 `spice`）—— 将来字段改名了，历史日志仍读得懂。

**时间窗**：默认 **30 天 + 200 条上限**，`.gte('created_at', since)` **让时间窗在服务端生效**（不是拉全量再本地裁）；「看更早的 ›」按 **×3** 扩窗（30 → 90 → 270 → 封顶 365 天）。

### 6.5 云连接与迁移

**唯一来源 `utils/cloud.js`**：`PUBLIC_CONFIG` / `getCloud` / `getDB` / `unwrap`。

抽出来的原因：`utils/orders.js` 原本自带一整套 SDK 加载 / 客户端实例 / 诊断包装。订单与日志连的是同一个云，**两处各写一套迟早出现「订单连得上、日志连不上」这种极难排查的问题**。

顺带把 **SDK 改成懒加载** —— `require('utils/cloud.js')` 现在零副作用，纯本地的模块（如 `utils/dishes.js`）可以放心引用日志模块，**单测和静态检查里也不必装 SDK 桩**。

**加订单字段的流程**：

```

2. MCP workbuddy_cloudservice_db_exec_sql（mode=migrate）执行
```

> 真机部署时新表记得**两个角色都授**（`authenticated` 与 `anon`，实际落到 `anon`，原因见迁移 `20260928160000_orders_anon_grant.sql`）。

### 6.6 订单的增量轮询（C8）

这块是整个项目**最费心思**的一段优化 —— 因为「实时」是轮询实现的，**每 15 秒就把全部订单的 JSONB 拉一遍**这件事，在小程序上是要还的账。

#### 查询有两条路

| 路径 | 做什么 |
| --- | --- |
| **全量 `listOrders`** | `select('*')` + `order('created_at', DESC)` + `range(0, 199)`（上限 `MAX_ORDERS = 200`） |
| **增量两步**（`utils/order-sync.js`） | ① `listOrderHeads`：只 `select('id,status,updated_at')` —— **三列标量，一个 jsonb 都不带**<br>② `listOrdersByIds`：`in('id', ids)` **一条请求批量**，只为「新的 / 变了的」发 |

一轮轮询的请求数从「每次 1 个巨型响应」变成「1 个轻量头 + 1 个只为变动项发的详情批」，**没有变动时连详情批都不用发**。

#### 三条不可动摇的约束

**① 等价不变式**

> 增量拼出来的 `orders` 必须与全量 `listOrders` **逐字节一致**。
> （顺序 = 头顺序 = `created_at DESC`、上限同 200。）

守住它 → `live.js` 的 watcher / `snapshot` / `diff` / 页面层**零改动**。这条不变式是「优化不改变行为」的保证 —— 只要它成立，这层优化就对上层完全透明。

**② 失败不推进基准**

详情批失败就抛给轮询退避（基准不动）；某条少返回就**保持旧值**且不记进基准 → 下轮重试。

> 否则那次更新**永久丢了且不报错** —— 这是最坏的一类 bug。

**③ `headsUsable()`**

轻量头没带回 `updated_at`（全是 0）→ **退回全量**。

> 否则增量会永远认为「没变化」，页面**静默失去实时性**（不报错，最难查）。

#### 为什么不用「时间窗」或「砍字段」

试过这两条路，都不行：

- **时间窗**会让订单页的老订单凭空消失（要么伤功能，要么再加一套「加载更早」），而且**并不降低单条订单的大小**。
- **字段裁不掉**：订单页要 `review.decorateItems(o.items, reviews)`、待做卡片要菜名、`frequency.js` 靠 `items` 数频率、`deadline.js` 要数份数；`frequency.js` 还依赖「最近 200 单」这个范围。

> **病根不在字段多，在于每轮重拉那些根本没变的。**

#### 入参校验：不能只判 `isNaN`

一个很值得记的坑：

```js
Number('')    // 0
Number(null)  // 0
Number(true)  // 1
```

只判 `isNaN` 会让空值变成 `in.(…,0)`、布尔垃圾查成一条真订单。

**正解**：先要求 `typeof` 是 `string` / `number`，再要求**正整数**（订单 id 是 bigint identity，从 1 起）。

```js
function isValidId(v) {
  if (typeof v !== 'string' && typeof v !== 'number') return false
  return Number.isInteger(Number(v)) && Number(v) > 0
}
```

改 `listOrderHeads` 的列名之前，先读它上面的注释块 —— 少了 `updated_at` 就会静默失去实时性。

### 7.1 统一出口

页面层不关心数据到底来自本地还是云端 —— 两类数据对页面都是同样的 Promise 形状：

```js
const data = await api.call('listDishes', { category: '经典热菜', keyword: '鸡' })
```

### 7.3 加新接口的步骤

```js
// 1. utils/orders.js 里写一个函数，挂进 ACTIONS 表
const ACTIONS = { /* … */ myNewAction: myNewAction }

// 2. 把 action 名加进 utils/api.js 的 ORDER_ACTIONS 数组
const ORDER_ACTIONS = [ /* … */ 'myNewAction' ]
```

漏了第 2 步 → 页面调的时候会抛「未知的 action」。

> **顺手要更新的护栏**：加 action 会让 `test_csv.js`（`dishes.ACTIONS` 个数）、
> `test_local_dishes.js`（`api.DISH_ACTIONS`）、`test_orders_workbuddy.js` / `test_review.js`
> （`orders.ACTIONS`）变红 —— **改计数并写明原因，别删断言**。

### 7.4 写操作必须校验影响行数

这条是硬规则。

```js
// utils/orders.js
function affectedRows(res) {
  return Array.isArray(res) ? res : (res && res.data) || []
}
```

**为什么必须有**：云服务被 RLS 拦下时返回的是**空数组而不是错误**。

于是「没写进去」和「写成功了」在返回值上长得一模一样。不校验的话，页面会弹出「已保存」而数据根本没进库 —— 用户以为成了，实际什么都没有，这类 bug 极难被发现，因为**任何一层都没有报错**。

所有写路径都走这个校验，拿不到行数就抛错：

```js
const rows = affectedRows(await getDB().from(TABLE).update({...}).eq('id', id).select())
if (!rows.length) throw new Error('这一单没能更新，可能已经被删掉了')
```

## 八、权限模型

这个项目里有**两套**权限，性质完全不同，别混在一起看：

| | 管什么 | 在哪落地 | 是不是安全边界 |
| --- | --- | --- | --- |
| **数据库权限** | 谁能读写库里的表和行 | PG 的 `GRANT` + `RLS` | **是** |
| **产品权限** | 哪个身份能点哪个按钮 | 页面 + 数据层 + 规则层 | **不是**（防手滑） |

### 8.1 数据库两层

PostgreSQL 的权限是**两层**的，**两层都通过才成功**：

| 层 | 内容 | 说明 |
| --- | --- | --- |
| 第一层 | 表级 `GRANT` | 决定这个角色「能不能碰这张表」 |
| 第二层 | 行级 `RLS 策略` | 决定这个角色「能碰表里的哪些行」 |

**`orders` 表**已启用 RLS，策略配为「**打开这个小程序的人可读、可写全部订单**」—— 因为订单是「两个人共享同一份」的语义，不需要按人隔离。

**`dish_logs` 表**只给 `SELECT` + `INSERT`（审计流水不该被改写）。

**`dishes` 表**策略 `dishes_couple_all` + `anon` / `authenticated` 的 ALL GRANT 都在。

两点必须知道的事：

> **RLS 的本质是「默认拒绝一切」。** 只要表启用了 RLS 却没有匹配的策略，**所有操作都会被拒绝**。
> 所以「表建好了但读不出来 / 写不进去」几乎一定是**策略没配或没配全**，而不是代码问题 —— 排查时先查策略，别读代码。

> **前端手里的 `publishableKey` 不是密钥。** 它只标识「是哪个应用」，本身不带任何权限；
> 真正的权限边界在数据库 RLS。**前端代码里永远不会出现有权限的密钥。**

这也是为什么这套架构能成立：小程序端直连数据库，但前端拿到的凭据「什么都干不了」，能不能写由数据库自己说了算。

### 8.2 产品权限三层

订单的权限边界写在**三处**，**改之前三处一起看**：

| 层 | 位置 | 规则 |
| --- | --- | --- |
| ① **页面** | `pages/orders`（按 `isCook` 出按钮）、`pages/todo` 卡片、`pages/order-edit`（`readonly = isCook \|\| done`） | 不给越权入口 |
| ② **数据** | `utils/orders.js` | `updateOrder` **不认 `status`**；`updateOrderStatus` **不认 `rejected`**；驳回走 `rejectOrder`（理由必填） |
| ③ **规则** | `utils/reject.js::canReject(status)` | **页面与服务端引同一份**，绝不各写一套 |

具体到两个身份：

| | 能做 | 不能做 |
| --- | --- | --- |
| **掌勺人** | 推进状态、驳回、收回驳回 | 改内容、删单 |
| **干饭人** | 改内容、删单、评价 | 改状态 |

**为什么三层都要有**：

- 只有 ① 不够 —— 将来加个新入口（比如「再点一单」复用编辑页）就绕过去了
- 只有 ② 不够 —— 用户会看到一个能点但点了报错的按钮，体验很差
- 只有 ①② 不够 —— 判定会漂移：页面写「开做中也能驳回」，服务端写「只有待开做能驳回」，两边不一致时行为不可预测

**回收驳回的判定**也收在一处（`REJECTABLE = [pending, cooking]`），它和「能推进的状态」**不是同一个集合** —— 开做中也能驳回（食材不够是常事），但已上菜不能。

### 8.3 身份与资料隔离

「我的资料」里的头像 / 称呼 / 个人介绍 / 当前状态 / 忌口清单 **按身份分开存**：

```
lovekitchen_nickname_cook      lovekitchen_nickname_orderer
lovekitchen_avatar_cook        lovekitchen_avatar_orderer
lovekitchen_intro_cook         lovekitchen_intro_orderer
lovekitchen_status_cook        lovekitchen_status_orderer
lovekitchen_avoids_cook        lovekitchen_avoids_orderer
```

**两套 key，互不干扰。** 编辑其中一方的基本信息不会改动另一方；换身份只是换一份资料来看。

这条曾经踩过坑：早期的称呼是共用的，结果「掌勺人改了自己的名字，干饭人下单的署名也跟着变了」（提交 `afad5b7` 修的）。

> 判断「哪些资料该分身份存」的标准很简单：
> **这个值在两个人身上是不是可能不一样？** 是 → 分开存。
> 昵称、头像、介绍、状态、忌口都满足；而购物车不是（它属于「这次点单」，不属于某个人）。

### 8.4 这不是安全边界

必须说清楚：

> 因为订单表 RLS 是「两人共享一份」，**服务端拿不到身份** —— 请求里没有可靠的身份信息。
> 所以要在这层做权限，只能靠前端传 `payload.role`，而**前端传的东西都可以伪造**。

因此这套产品权限是**防手滑的产品约定，不是安全边界**。它的目标是：

- 让两个人在同一台手机上操作时不会误触（她不会不小心把自己点的单推进到「已上菜」）
- 让界面清楚（不该她管的事，按钮就不出现）

**别试图伪造 `payload.role` 去服务端做校验** —— 那会给人「这里有安全防护」的错觉，而实际上没有。

真要做安全边界，得引入真正的身份体系（登录态 + user_id 与订单绑定 + RLS 按 user 过滤），那会让这个两人小工具复杂一大截。**这是一个有意识的取舍，不是疏漏。**

## 九、实时同步与到点提醒

### 9.1 为什么是轮询

复述一遍前提（很重要）：

> 云服务 SDK 只有 `database / auth / storage / llm` 四个模块 —— **没有 realtime、没有长连接、没有推送**。

小程序端拿不到任何推送通道。所以「实时」只能靠**前台轮询**逼近，而小程序关着的时候**收不到任何东西**。

既然是轮询，设计重点就是「**轮得聪明**」：不该轮的时候别轮、该轮的时候别白轮、出错了别猛敲。

### 9.2 轮询器只有一个

起在 `app.js` 的 `onShow`，退到后台立刻 `onHide` 停掉：

```js
App({
  onShow() {
    if (store.getRole()) {
      live.watch({
        role: () => store.getRole(),        // 传函数而不是值 —— 切身份后不用重建 watcher
        onTick: (d, orders) => deadline.check(orders),  // 到点提醒挂在这条轮询上
      })
    }
  },
  onHide() { live.unwatch() },   // 后台的定时器会被系统限流，留着只会耗电
})
```

**页面不各开各的轮询**，只做两件事：**订阅数据把列表重画一遍** + **发现变化时浮一句话提示**。

这么做的直接好处：**底栏角标在任何 tab 页都实时** —— 我在菜单页翻菜谱时也能看到待做数往上跳。

### 9.3 三档节奏跟着注意力走

`utils/live.js` 的 `INTERVALS`：

| 情况 | 间隔 |
| --- | --- |
| 掌勺人有待开做的单 / 干饭人有菜在做或有单被驳回 | **15s** |
| 有事但不急（比如还有单没上菜，但没在做的） | **30s** |
| 全都上完菜了 | **60s** |

「已驳回」是单独一档：它**不计入**掌勺人的「等着开做」，也不用他做任何事；但干饭人要看一眼（改单或删掉），所以进干饭人的角标、也走 15 秒那一档。

**失败退避**：连续失败按 15s → 30s → 60s → **120s** 翻倍，成功后立刻回到正常档 —— 断网时不能死循环猛敲接口。

**手动操作直接插队**：下拉刷新、重试、「开始做 / 做好了」这类用户主动发起的动作会**强制补一轮**，不受档位限制。用户点了按钮就该立刻看到结果，不能等 15 秒。

### 9.4 变化检测 = 快照 + 差异

每轮把订单列表压成一份快照：

```js
{ [id]: { status, dishes, qty, reviews, dine } }
```

再和上一份比，算出「新来几单 / 哪单改状态了 / 哪道菜被评价了」。

**首轮只建基线、不报任何变化。** 否则一进页面就会把历史订单全算成「刚来的新单」，炸出一堆提示。

### 9.5 只在该说话时说话

变化会浮一条 **6 秒自动消失**的提示条 —— 不是 `showToast`，因为提示条**要能被点击跳转**。

同时底栏角标跟着跳。

**自己刚做的动作不播报**：掌勺人自己点的「开始做」不会再提示一遍，干饭人自己下的单也不提示 —— 重复播报纯属噪音。

### 9.6 一次请求办两件事

轮到的订单列表**直接喂给页面渲染** —— 「刷新列表」和「发现变化」共用同一次请求，不额外多发。

**弹窗期间临时暂停轮询**（列表不能在对话框底下自己变），离开页面时把暂停状态还回去，**不会把全局轮询锁死**。

> 这个「还回去」很容易漏：如果暂停时直接 `pause()`、离开时忘了 `resume()`，
> 全局轮询就永远停了 —— 而且**不报错**，表现是「从某个页面回来后就不实时了」。所以要成对写。

### 9.7 增量轮询的接线

`utils/order-sync.js` 提供增量视图，`live.js` 用它替代全量拉取。三条约束（等价不变式 / 失败不推进基准 / `headsUsable()`）见 [6.6](#66-订单的增量轮询c8)。

**守住等价不变式 → 上层的 watcher / snapshot / diff / 页面层零改动。** 这是这层优化能安全落地的前提。

### 9.8 到点提醒

**规则**：截止前 30 分钟，如果这一单**还没开做**（状态仍是 pending），掌勺人那边弹一次窗。

- 标题「⏰ 还有 25 分钟」
- 正文写清楚是谁的哪一顿、几点截止、几道菜
- 点「这就去做」直接落到待做看板；点「知道了」安静收起来
- 同一时刻多单到点 → **合成一个弹窗列出来**，不连环弹

**三条刻意的取舍**（理由都写在 `utils/deadline.js` 里）：

| 取舍 | 理由 |
| --- | --- |
| **只提醒掌勺人** | 「还没开始做」这件事只有他能动；提醒下单的人只会让她干着急 |
| **状态不是 pending 的一律不管** | 正在做 / 已上菜不必催；被驳回的单**球已经回到干饭人那边**（等她改了重新提交），这时候催掌勺人是催错人 |
| **窗口是 `[截止 - 30 分钟, 截止)`** | 过了截止就不再提醒 —— 那时候该看的是「哪单超时没做」，再弹一次「快到了」也来不及了 |

**每单只提醒一次**：提醒过的记在本地 `lovekitchen_reminded`（最多留 60 条），去重键是：

```
订单 id | 用餐日期 | 时段
```

干饭人把用餐时间改掉就是一件新的事，**值得再提醒一次** —— 所以日期和时段要进键。

**「该不该提醒」只有一处判断**：`utils/deadline.js::isDue` + `remindKey`。**页面只负责弹**。

> 一单只提醒一次靠 `store` 的去重键兜住。如果页面各写一套判定，
> 必然出现「这个入口弹两次、那个入口一次不弹」。

**顺序有个细节**：**先记「已提醒」再弹**。反过来的话，弹窗还没关的时候又轮询到一轮，就会再弹一次（`test_dine_deadline.js` 的 `pendingModal` 桩专门测这个场景）。

**提醒只可能在对方正开着小程序时出现** —— 因为挂在 App 级轮询上。好处是我翻菜单、看订单时都能被提醒到，不必停在待做页干等。

### 9.9 一个被顺带发现的空档

夜宵截止从原来的 24:00 提到 **23:30** 之后，出现了一个新情况：

> **23:30 ～ 24:00 之间，今天四个时段会全部关闭。**

这时「今天」会自动标灰、默认日期落到明天。不处理的话，会订出一单「今天的早餐」—— **永远做不出来**（今天已经过去了）。

这类「改了 A 导致 B 出现空档」的问题，是改时刻定义时最容易漏的。所以：

> **改 `constants.js::DINE_SLOTS` 的时刻，要连带想「今天是否四个时段全关」。**

用餐截止时刻是**分钟精度**，唯一定义在 `constants.js::DINE_SLOTS` 的 `endHour` + `endMinute`：

| 时段 | 截止 |
| --- | --- |
| 🌅 早餐 | 10:00 |
| ☀️ 午餐 | 14:30 |
| 🌙 晚餐 | 19:30 |
| ✨ 夜宵 | 23:30 |

**别在别处写 `hour * 60 + min`** —— 那是重复定义，两处迟早漂移。

## 十、样式体系

### 10.1 四层分层

```
styles/common.wxss   设计 token，写在 page {} 上        → app.wxss @import（全局）
styles/state.wxss    空态三态零件                        → app.wxss @import（全局）
styles/sheet.wxss    弹层基座                            → 页面 / 组件按需 @import
styles/tap.wxss      按压反馈零件 .tap-hover             → app.wxss @import + 4 个组件各自 @import
```

**`common.wxss` —— 设计 token**

写在 `page {}` 上：`--brand` / `--brand-2` / `--grad-main`（由前两者拼出）/ `--grad-hero` / `--grad-done` / `--grad-pink` / `--grad-warn` / `--grad-panel` / `--radius-card` / `--radius-pill` / `--shadow-card` / `--shadow-float`；外加辣度皮肤 `.spice-0 .. .spice-3`。

> **颜色 / 渐变 / 圆角 / 阴影只在这里写一次**，其余一律 `var()`。

主题色直接取自小程序本体：主色 `#FF7A9E`、辅色 `#FF9F43`、文本 `#3B2B31`、底色 `#FFF7F3`。

**`state.wxss` —— 空态零件**

`.state` / `.state-emoji` / `.state-tip` / `.state-sub` / `.btn-retry`。

> **刻意不用 `var()`、刻意不含 `page` 选择器** —— 组件的 wxss 里不能出现 `page` 选择器，而组件又必须能 `@import` 它。

**`sheet.wxss` —— 弹层基座**

`.mask` / `.sheet` / `.sheet-head|title|close|back|dish|emoji|name` / `.cats` / `.cat` / `.cat-active` + `@keyframes sheet-up`。

`pages/menu/menu.wxss` 与 `components/dish-picker` 都 `@import` 它 → **全仓库只剩一处 `.sheet` 定义**。

> **历史教训**：menu 与 order-edit 曾各有一份 `.sheet`，且数值已经漂移 ——
> 底色 `#FFFCFB` vs `#FFF7F3`、padding `32/32/48` vs `28/24/40`、头部间距 `8rpx` vs `20rpx`。
> 两份定义各自演化，最后同一个弹层在两个页面长得不一样。

**`tap.wxss` —— 按压反馈**

```css
.tap-hover { opacity: 0.7; transform: scale(0.98); }
```

### 10.2 组件样式隔离：变量能穿透，类名不能

这是理解整套样式分层的关键：

> **CSS 变量是继承属性，能穿透组件边界；类名不能。**

所以跨组件共享「颜色 / 圆角 / 阴影」用的是 **CSS 变量**（定义在 `page {}` 上，组件内 `var()` 直接可用）；而跨组件共享「结构类」（`.state` / `.tap-hover` / `.sheet`）必须**在每个组件的 wxss 里 `@import`**。

两条推论：

- 组件默认样式隔离，**别指望 `styleIsolation: apply-shared`** —— 它和 `@import` 的行为不一样，容易在真机上出现「开发者工具里好好的、真机上没样式」
- `hover-class` 用到的类**也必须 `@import` 进每个组件**，否则按压反馈静默失效

### 10.3 两个会静默失效的坑

**坑一：页面样式表后加载，会覆盖全局同名类**

同样特异性下，页面 wxss 里的定义会盖掉全局的。

> **要统一某套皮肤时，不仅得删掉重复定义，还得删掉页面里的覆盖声明。**

例子：`todo.wxss` 里的 `.oi-spice { color: #ffffff }` 会盖掉全局 `.spice-0` 的字色 —— 留着它，统一皮肤就是白做（而且**看起来一切正常**，因为不报错）。

**坑二：组件的 wxss 里不能出现 `page` 选择器**

组件内没有 `page` 节点。所以 token 段和零件段**必须拆成两个文件** —— 这就是 `common.wxss`（含 `page {}`）与 `state.wxss` / `tap.wxss`（不含 `page`）分开的原因。

> 官方还明确：**组件 wxss 里不能用 ID / 属性 / 标签名选择器**（类选择器没问题）。

### 10.4 兼容性约定

同 `app.wxss` 顶部，六条，都踩过真机：

| 约定 | 原因 |
| --- | --- |
| **不用 flex `gap`** | 安卓 XWeb 低版本不支持；用负外边距容器替代 |
| **安全区 `constant()` + `env()` 双写** | 全站 17 处一一配对；改完跑 `.workbuddy/tmp/fix_safe_area.py` 补漏，或跑 `test_p0_fixes.js` 的 A 组护栏 |
| **字号下限 22rpx** | 再小真机上看着费劲 |
| **自定义 tabBar 是原生层，页面盖不住** | 弹层要用 `setHidden()` 让位 |
| **按压反馈用 `hover-class`，不用 CSS `:active`** | 真机上 `:active` 常常不触发 |
| **wxml 属性名用 kebab-case** | 会自动转驼峰（`spice-levels` ↔ `properties: { spiceLevels }`） |

### 10.5 接线点变多带来的新问题

组件化之后，「点了没反应」成了最难查的一类问题（组件事件没接上、`bind` 名字写错、`@import` 漏了）。

对策是把它变成**可自动检查的**：`test_batch4.js` 的 F 组会把 wxml 里每个 `bind*/catch*="fn"` 的名字**回查对应 js 里有没有定义**。

> **扫 wxml 前必须去掉 `<!-- -->`** —— `state-block.wxml` 头部注释里就有 `bind:retry="loadDishes"` 这种用法示例，会被误判成真接线（假红）。

## 十一、质量保障

### 11.1 为什么是「契约测试」

这个项目**没有单元测试框架，也不依赖微信开发者工具** —— 护栏是 37 个纯 node 脚本（`.workbuddy/tmp/test_*.js`），直接 `require` 真实的业务模块跑断言。

选择这套方式的原因很具体：

1. **小程序代码没法在 node 里直接跑** —— 所以要搭一层假环境（wx 桩 + 假 SDK），反而逼着业务逻辑往**纯函数**方向抽（`todo.js` / `review.js` / `csv.js` / `frequency.js` / `reject.js` / `paging.js` / `dish-search.js` 都是纯函数，正是为了可测）
2. **不想引入构建链** —— 两个人的小工具，加一套 test runner + babel + mock 库不划算
3. **契约测试比单元测试更贴合这个项目的风险** —— 真正的风险不是「某个函数算错了」，而是「**两个文件之间的约定漂移了**」（比如 `itemKey` 在编辑页和评价页写法不一致、状态字面量散落各处）

### 11.2 运行方式

```bash
cd .workbuddy/tmp && node test_xxx.js                          # 单个
cd .workbuddy/tmp && for f in test_*.js; do node "$f"; done    # 全量
```

**判定是否全绿用「❌ 计数」而不是看摘要行** —— 各文件摘要格式不统一（有 `通过 58 项，失败 0 项`、有 `通过 132 / 失败 0`），用 ❌ 计数最稳：

```bash
cd .workbuddy/tmp && red=""; ok=0; for f in test_*.js; do
  out=$(node "$f" 2>&1); bad=$(echo "$out" | grep -c "❌")
  if [ "$bad" != "0" ]; then red="$red $f($bad)"; else ok=$((ok+1)); fi
done; echo "OK=$ok"; echo "RED=$red"
```

**当前状态：37 个文件、共 2,242 项断言，全部通过（零失败）。** 全量跑一轮约 2 分钟。

> 这 2,242 项**不含** `test_cloudfn.js` 与 `test_orders_pg.js` —— 它们测的是已废弃架构，
> **长期红着，不是回归**（见 [14.1](#141-已废弃的架构不要再回头走)）。

### 11.3 静态体检三件套

改动后必跑（它们查的是「语法 / 结构 / 兼容性」这类测试跑不出来的问题）：

| 脚本 | 作用 |
| --- | --- |
| `audit_wxml.py` | wxml 标签配平 |
| `audit_pack.py` | 上传包体检：白名单体积、逐文件 JS 语法 |
| `test_style_compat.js` | 样式兼容契约（不用 flex gap / 安全区双写 / 字号下限 / `:active` 等） |

> **`audit_wxml.py` 必须逐字符扫描，不能用正则** ——
> 自闭合的 `<state-block … />` 会被正则误报「未闭合」。

### 11.4 假环境怎么搭

搭得对不对，直接决定护栏是真是假。六条：

| 要点 | 说明 |
| --- | --- |
| **wx 桩** | `require` 页面模块前把 `global.Page` / `global.Component` 设成捕获定义的函数，每次 `delete require.cache` 重新装载；`setData` 桩**必须支持 `'a.b'` 路径写法** |
| **假 SDK 拦截 require** | `utils/cloud.js` 是**懒加载**（`require('./cloud')` 零副作用），所以纯本地模块的单测**不必装 SDK 桩**；要测云路径时在 `require` 前拦截包名 |
| **假 SDK 桩必须按表分开存** | `cloud.rows` 一个数组装所有表的话，「云端表里有几行」的断言会被 `dish_logs` 的日志行污染。要 `cloud.tables = { dishes: [], dish_logs: [] }` |
| **失败开关要设成「粘住」的**（不自动消耗） | `saveDish` 里 `dishLogs.record` 也是一次 fire-and-forget insert，先被吃掉的话，被测的那次 `pushAdd` 反而成功了 |
| **假云端必须返回深拷贝** | `io.orders.slice()` 只换了数组、**元素还是同一批引用** —— 测试里改 `data[0]` 会连带改到被测模块的缓存（**得到假红**）。真机每次响应都是新反序列化的对象，桩要照着仿真 |
| **弹窗用「可手动应答的 `showModal` 桩」** | 不能自动回调，否则测不了「弹窗还开着时又轮询到一轮」 |

### 11.5 五条「做不到就是假护栏」

这份清单是踩出来的 —— **每一条都曾经产生过「绿色的假护栏」**：

**① 时序行为必须做行为测试**

防抖 / 节流 / 重入不能只检查「代码里有没有 `debounce`」。「连打 5 个字符只过滤 1 次」要**包装 `applyFilter` 计数** + `await sleep(280)` 来验证。

并发保护的判据用「**`loading` 有没有被重新置 true**」，**别自己数调用次数**（容易从不自增、断言空转 —— 那就等于没测）。

**② 别写「复刻一份实现」的测试**

`test_menu_search.js` 原先抄了一份 `applyFilter` —— **测的是副本，真实现漂移它不会红**，比没护栏更危险。抽成 `utils/dish-search.js` 之后改成 `require` 真实现。

> 判断标准：**测试里有没有出现被测逻辑的第二份实现？** 有 → 这条护栏是假的。

**③ 别用会被自己骗到的写法**

| 假红来源 | 例子 |
| --- | --- |
| 正则遇多行写法失配 | `api\n  .call(…)` 匹配不上单行正则 |
| class 精确匹配漏掉模板写法 | `class="ps"` 匹配不上 `class="ps {{…}}"` |
| 查「不该出现的标识」命中**自己刚写的注释** | 需要 `stripComments`；wxml 还要去 `<!-- -->` |
| 切片锚点命中**无关 handler** | 同名属性在别的 handler 里也有 → 用 `indexOf('\n  fnName() {')`，别用调用点 |

**④ 先取出整个标签再查属性**

**属性值里合法地出现 `>`**（`rating >= s`、`list.length > 0`）—— 对标签用 `[^>]*` / `[\s\S]{0,N}` 都会**提前截断**，断言假红。

正解：`lastIndexOf('<', i)` ~ `indexOf('>', i)` 取出标签，再在标签内查。

**⑤ `const` 没有变量提升（TDZ）**

抽常量时 `require` 必须放在**第一次使用之前**，否则模块加载直接：

```
ReferenceError: Cannot access 'X' before initialization
```

整个 require 链全炸（`utils/orders.js` 踩过，**连带 18 个测试文件红**）。

### 11.6 护栏变红时怎么办：改断言，不删断言

> **重构与新增必然让某些断言变红，那是护栏该有的行为。**

| 改动 | 会红的护栏 | 正确做法 |
| --- | --- | --- |
| 改 class / 渐变字面量 / 下标名 | `test_batch4` 等结构类断言 | 更新断言指向新写法（`bind:retry` / `var(--grad-main)` / `data-id` / `STATUS.cooking`） |
| 结构搬进组件 | `test_checkout_contract.js`（20+ 条） | 断言**一起搬**到 `components/cart-list/cart-list.wxml` —— 组件两页共用，**破坏它同时坏两页** |
| 加一个 action | `test_csv.js`（`dishes.ACTIONS` 个数）、`test_local_dishes.js`（`api.DISH_ACTIONS`）、`test_orders_workbuddy.js` / `test_review.js`（`orders.ACTIONS`） | 更新计数**并写明原因** |
| 加一个页面 | `test_csv.js`（pages 计数）、`test_orders_workbuddy.js`（pages 清单）、`test_ui_helper.js`（**每页都必须 `require('../../utils/ui')`**，哪怕只用 `ui.haptic`） | 同步三处 |
| 魔法值换成常量 | `test_live` / `test_todo` / `test_order_roles` / `test_roles` / `test_review` / `test_final_order` | 断言改指常量，**不删** |

**改完一批先看断言总数有没有掉 —— 掉了说明护栏被顺手删了。**

### 11.7 为什么这些测试不进仓库

`.workbuddy/` 整个目录是 **gitignore** 的 —— 测试、静态脚本、优化清单、工作日志都在里面，**不进版本库**。

这是既有约定，理由有两条：

1. 它们是**开发期资产**，不影响小程序运行，进仓库只会让上传包体检和 `git status` 变吵
2. 它们**依赖本机路径与 node 环境**，别人 clone 下来也不一定能跑

代价要认：**测试不进仓库 → clone 的人拿不到护栏**。所以本文档把测试的**方法**（假环境怎么搭、五条假护栏、变红处理表）写进了 `docs/testing-guide.md`（**这份在仓库里**），让人能重建。

### 11.8 质量流程小结

一次完整改动之后要跑的东西：

```
1. 全量契约测试（37 个文件，看 ❌ 计数 → 期望 0）
2. audit_wxml.py          标签配平
3. audit_pack.py          上传包体检（体积 / JS 语法）
4. test_style_compat.js   样式兼容契约
5. 改样式的话另外跑 test_p0_fixes.js（安全区双写护栏）
```

### 12.5 常见问题速查

| 现象 | 排查顺序 |
| --- | --- |
| 「暂不支持 npm 模块」 | ① 确认 `miniprogram_npm/@tencent-ai/workbuddy-cloud-sdk/index.js` 存在 → ② 重新编译 → ③ 清除缓存 + **关闭项目重新打开** → ④ 仍不行就 `npm install` + 构建 npm |

| 菜单没加载出来 | 菜单是内置数据，正常不会出现。检查是否改坏了 `data/dishes.js`（看 Console 报错） |

**关于费用**：云服务有免费额度（数据库读写量、存储量等），两人日常点菜的用量远够不到上限。

## 十四、已知边界与路线图

### 14.1 已废弃的架构（不要再回头走）

`utils/api.js` 的头部注释里明确记着两条已废弃路径，防止后来者重新踩：

| 废弃方案 | 为什么不行 |
| --- | --- |
| **云函数**（`wx.cloud.callFunction`） | 云函数环境不注入登录态，以匿名身份访问数据库**能读不能写** |
| **自建 CloudBase 环境** | 要求环境绑定当前小程序 AppID；本项目用的环境 `WxAppId` 为空，绑不上 |

> **`test_cloudfn.js` / `test_orders_pg.js` 测的就是这两条废弃架构，长期红着** ——
> 它们不是回归，也不该去修。

### 14.2 已知边界

诚实列出做不到的事：

| 边界 | 原因 | 影响 |
| --- | --- | --- |
| **小程序关着收不到任何推送** | SDK 没有推送通道 | 提醒只可能在对方正开着小程序时出现 |
| **「实时」有最多 15~60 秒延迟** | 轮询实现 | 对方操作后最差要等一轮；手动操作会立刻补一轮 |
| **订单最多显示最近 200 条** | `listOrders` 的 `range(0, 199)` | 超出后看不到更早的（两人日常远够不到） |
| **干饭人加的菜不会同步到掌勺人菜单** | 单向链的刻意取舍 | 下单时菜名进 `items` 快照，掌勺人照样看得到 |
| **产品权限不是安全边界** | 服务端拿不到身份 | 防手滑，不防伪造 |
| **只认 UTF-8 的 CSV** | 中文 Windows 的 Excel 默认存 GBK | 页面检测到替换字符会直接提示「另存为 UTF-8」 |
| **菜单本地优先 → 两台手机可能不一致** | seed 相同但 override 各存各的 | 有 `dish_logs` 能看出对方动过什么 |

- [ ] 菜品图片上传

- [ ] 吃完打卡 / 美食日记

| 值 | 含义 |
| --- | --- |

### 附录 C：四条必须在同一处实现的规则

这四条是最容易踩的 —— 它们的共同点是「**换个地方重写一遍，两份就会漂移，而且漂移后不报错**」。

| # | 规则 | 唯一定义 | 漂移的后果 |
| --- | --- | --- | --- |
| 1 | **菜品行唯一键 = `dishId\|辣度`**（`dishId` 缺失回退菜名） | `utils/review.js::itemKey` | `pages/order-edit` 的 `itemKey` 必须与它**字面一致**；漂移后「按 A 存、按 B 读」，**数据在页面上凭空消失** |
| 2 | **推进订单状态只有一条路径** | `api.call('updateOrderStatus', {id, status})` | 待做 / 订单 / 详情三页共用；各写一套会出现某页推了状态但没写 `updated_at` → 实时同步失效 |
| 3 | **写操作必须校验影响行数** | `utils/orders.js::affectedRows()` | RLS 拦下时返回**空数组而不是错误** → 不校验就会「提示成功但没写进去」 |
| 4 | **「该不该提醒」只有一处判断** | `utils/deadline.js::isDue` + `remindKey` | 页面各写一套必然「这个入口弹两次、那个入口一次不弹」 |

## 结语

这个项目的规模不大 —— 11 个页面、约 1.7 万行代码、两个人用。但它把「两个人一起吃饭」这件事里所有会卡住的地方都认真处理了一遍：

- 她会忘记菜名 → 搜索支持食材
- 她微辣我特辣 → `dishId|辣度` 唯一键
- 她不吃香菜 → 忌口跟着订单上云
- 她点了但我在忙 → 到点提醒
- 我做不了这顿 → 驳回必须说理由
- 她改了菜单我不知道 → 日志表留痕
- 两台手机数据对不齐 → 分号段 + 单向链

**每一个功能背后都是一个真实发生过的小摩擦。**

技术上也一样：后端换了三次才找对路、实时只能靠轮询、菜单本地优先有代价 —— 这些都不是「最佳实践」，而是在**具体约束下做出的具体选择**，文档里把这些约束和代价都写下来了。

这也是这份文档存在的意义：**代码能说明「是什么」，「为什么」只能靠写下来。**
